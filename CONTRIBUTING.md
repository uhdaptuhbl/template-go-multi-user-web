# Contributing

`CLAUDE.md` is this project's constitution: the development model, the code and
test standards, and the definition of done all live there, and this file does
not restate them. Read it before your first change. What follows is only how to
get set up and what the mechanics are.

## Setup

You need Go at the version `go.mod` names. Everything else, golangci-lint
included, is pinned as a tool in `go.mod` and needs no global install:

```sh
go tool mage -l
```

lists every build target. `goreleaser` is needed only if you touch the release
configuration.

## Before you open a pull request

```sh
go tool mage race
go tool mage lint
go tool mage integration
```

All three must pass. CI runs the same checks plus a build, a vulnerability scan
(`go tool mage vuln`), a tidy check, and checks on the container image and the
release configuration, so running them locally only saves you a round trip; it
does not replace the gate. The linter CI runs is the one `go.mod`
pins, so a finding cannot appear in CI that did not appear locally. The full
definition of done, including the traceability requirement, is in `CLAUDE.md`.

## How a change is shaped

A change that adds or alters behaviour is specified before it is written. The
three documents and the phases they belong to are described under "Development
model" in `CLAUDE.md`; the templates are in `specs/templates/`. A typo, a
dependency bump, or a one-line fix needs none of that.

An architectural decision gets a record in `docs/adr/`, written at the time the
decision is made rather than reconstructed afterwards. An open decision is
recorded as `proposed` so the options are in version control instead of in
someone's memory.

## Commits

[Conventional Commits](https://www.conventionalcommits.org/), because release
notes are generated by grouping on the type prefix. A commit whose subject does
not parse ends up under "Other" in the next release.

```
feat(server): add a readiness endpoint
fix(config): reject an empty listen address
build(deps): bump golang.org/x/net
```

Keep commits atomic. A commit that does two things cannot be reverted for one
of them.

## Branches

Short-lived, off `main`, which stays releasable. Rebase rather than merge
`main` into your branch, so the history stays readable and the generated
release notes stay honest.

## Releasing

Maintainers only; the procedure and the pre-tag rehearsal are in `README.md`
under Releases.
